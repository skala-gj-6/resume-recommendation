# 백엔드 구현 범위와 합의 필요 사항

이 문서는 현재 합의된 사용자 흐름을 Spring 백엔드 작업으로 옮기기 위한 체크리스트입니다. DB와 API의 상세 계약은 [DB 개요](../db/README.md), [API 개요](../api/README.md)를 기준으로 합니다.

## 1. 현재 준비된 기반

| 영역 | 현재 상태 |
|---|---|
| PostgreSQL | Docker Compose 서비스와 영속 볼륨 준비됨 |
| Mock Recruitment Provider | 공고 목록·상세·전체 카드 필드를 가진 고정 추천 API 실행 가능 |
| 기업 정보 | `COMPANY`, `COMPANY_INFO` 엔티티·Repository와 30개 기업/60개 정보 시드 준비됨 |
| Spring 외부 연동 | 공고 상세·추천 후보를 호출하는 `RecruitmentProviderClient`와 타임아웃·예외 변환 구현됨 |
| 테스트 DB | H2 프로필과 기본 통합 테스트 환경 준비됨 |
| 사용자·경험 | 고정 데모 로그인, 경험 구조화 미리보기·저장·조회·수정 구현됨 |
| 추천 | 실행·입력 스냅샷·결과 저장과 최신/상세 조회 구현됨 |
| 지원 프로젝트 | 공고/문항 스냅샷과 기존·신규 프로젝트 조회 구현됨 |
| 자기소개서 | Spring AI의 OpenAI GPT-4o Structured Outputs와 문항별 비동기 초안·Polling·선택·수정·검토 구현됨 |

실제 인증과 사용자 선호 정보 API는 아직 구현하지 않았습니다. 경험 구조화와 초안 생성은 런타임 Mock 없이 Spring에서 OpenAI를 직접 호출하며, 비로그인 공고 목록·상세는 계속 프론트엔드가 Mock API를 직접 조회합니다.

현재 목데이터의 30개 기업은 모두 기업 정보가 있지만 공고 상세은 `responsibilities`, `preferredQualifications`가 비어 있고 `educationLevel`이 없습니다. 백엔드와 프론트엔드는 빈 값도 정상 응답으로 처리해야 합니다.

## 2. 반드시 구현할 백엔드 기능

### 2.1 스키마와 공통 기반

- ERD에 정의된 엔티티, Repository, 고유 제약, 조회 인덱스를 구현합니다.
- 현재 데모는 JPA `ddl-auto=update`로 스키마를 생성합니다. 운영 전 Flyway 같은 마이그레이션 도구와 `ddl-auto=validate`로 전환합니다.
- 공통 오류 응답, Bean Validation, 현재 데모 사용자 조회 방식을 구현합니다.
- 모든 사용자 소유 리소스는 요청 본문의 `userId`가 아니라 서버가 결정한 현재 사용자로 조회합니다.

필요한 신규 도메인:

```text
USERS와 선호 정보
EXPERIENCE / EXPERIENCE_KEYWORD
RECOMMENDATION_RUN
RECOMMENDATION_INPUT_EXPERIENCE
RECOMMENDATION_ITEM
JOB_APPLICATION
COVER_LETTER_ITEM
COVER_LETTER_DRAFT
COVER_LETTER_EDIT
DRAFT_EXPERIENCE
DRAFT_COMPANY_INFO_SNAPSHOT
LLM_CALL_LOG
```

### 2.2 데모 로그인과 경험

- 로그인 버튼이 고정 데모 사용자 토큰 또는 세션을 반환하게 합니다.
- 자유서술 경험을 LLM로 STAR 구조화하되 구조화 API에서는 저장하지 않습니다.
- 확인된 구조화 결과 또는 사용자가 직접 작성한 STAR 입력만 저장 API에서 영속화합니다.
- 경험 목록·상세·수정 API와 키워드 동기화를 구현합니다.
- 삭제 API는 화면 범위에 포함할 때만 구현해도 됩니다.

### 2.3 추천 제공자 추상화와 결과 저장

공고 조회와 추천 계산은 교체 시점이 다르므로 인터페이스를 분리하는 편이 안전합니다.

```text
PostingProvider
└─ getPosting(externalPostingId)

RecommendationProvider
└─ recommend(experiences, limit)
```

현재 Mock 어댑터가 두 인터페이스를 모두 구현할 수 있습니다. 향후 추천 계산만 바꾸면 `RecommendationProvider` 구현체만 교체합니다.

구현 항목:

1. 현재 사용자의 저장 경험과 키워드를 조회합니다.
2. `RECOMMENDATION_RUN(PROCESSING)`과 입력 경험 스냅샷을 저장합니다.
3. 설정으로 선택된 추천 제공자를 호출합니다.
4. 제공자 응답을 공통 모델로 변환하고 필수값, 중복 공고, 순위, 점수를 검증합니다.
5. 외부 기업 ID를 내부 `COMPANY`에 매핑합니다. 현재 Mock 카탈로그에서 매핑 실패는 fixture 오류이므로 실행 전체를 실패시킵니다.
6. 카드 표시 스냅샷과 추천 근거를 `RECOMMENDATION_ITEM`에 저장합니다.
7. 실행을 `COMPLETED` 또는 `FAILED`로 종료합니다.
8. 생성 응답, 최신 결과 조회, 특정 실행 조회, 추천 공고 상세 조회 API를 제공합니다.

설정 예시:

```yaml
app:
  recommendation:
    provider: mock
    result-limit: 10
```

현재 Mock 추천 응답에는 목록 카드 필드가 부족하므로 기업명, 직무 분류, 업종, 지역, 경력, 고용 형태, 마감일, 활성 여부, 키워드, 원문 URL, 추천 이유를 추가해야 합니다. Spring DTO와 Mock 응답을 동시에 변경합니다.

### 2.4 지원 프로젝트와 문항

- `externalPostingId`로 현재 사용자의 기존 프로젝트를 조회할 수 있게 합니다.
- 사용자가 기존 프로젝트 대신 새로 만들기를 선택하면 동일 공고라도 새 `JOB_APPLICATION`을 생성합니다.
- 추천 목록에서 시작했다면 `sourceRecommendationItemId`의 소유권과 공고 ID 일치를 검증하고 선택적으로 연결합니다.
- 최신 공고 상세를 조회한 뒤 공고와 문항을 한 트랜잭션으로 스냅샷 저장합니다.
- 공고 문항에는 `question_source=POSTING`, 직접 입력 문항에는 `MANUAL`을 저장합니다.
- 공고 문항이 있는데 직접 입력을 함께 보내거나, 공고 문항이 없는데 직접 입력도 없으면 검증 오류를 반환합니다.
- 프로젝트 목록·상세 API에서 화면 제목과 문항별 최신·선택 초안 요약을 제공합니다.

### 2.5 문항별 AI 초안과 수정본

- LLM 호출 코드는 `CoverLetterGenerator` 같은 인터페이스 뒤에 둡니다.
- 생성 요청 시 새 `COVER_LETTER_DRAFT(PENDING)`를 먼저 만들고 `202 Accepted`를 반환합니다.
- 백그라운드 작업에서 `GENERATING`으로 전환한 뒤 문항별 초안을 하나씩 생성합니다.
- LLM의 구조화 응답을 검증하고 실제로 사용한 경험·기업 정보를 스냅샷으로 저장합니다.
- 성공·실패 상태 조회 API를 제공해 프론트엔드 Polling을 지원합니다.
- 새 초안은 기존 초안과 수정본을 보존하며 별도 `draft_no`를 가집니다.
- 사용자는 완료된 초안을 선택할 수 있고, 수정본은 명시적인 저장 버튼 요청에만 upsert합니다.

### 2.6 테스트와 운영 보호장치

- 추천 실행 성공·실패와 입력 경험 스냅샷 통합 테스트
- 동일 추천 실행 내 공고·순위 중복 검증 테스트
- 다른 사용자의 추천·경험·프로젝트 접근 차단 테스트
- 동일 공고에 프로젝트 여러 건 생성 가능한 테스트
- 공고 문항과 직접 입력 문항 분기 테스트
- 새 초안 요청이 기존 초안을 덮어쓰지 않는 테스트
- 비동기 성공·실패와 서버 재시작 후 정체 작업 복구 테스트
- OpenAI 타임아웃·재시도와 잘못된 구조화 응답 테스트
- 추천 제공자 구현체 교체 시 공통 계약 테스트

## 3. 현재 구현하지 않아도 되는 기능

- 실제 추천 점수 계산 알고리즘
- 사람인·잡코리아 실제 제휴 API
- 공고 마스터 DB와 공고 수집 배치
- 실제 OAuth, 비밀번호 로그인, 다중 사용자 운영 기능
- 추천 이력 관리 화면과 추천 결과 개별 수정 API
- 전체 문항 일괄 초안 생성과 생성 그룹
- 별도 문항 사전 분석 API·테이블
- 수정본 전체 버전 이력과 자동 저장
- SSE 스트리밍
- 기업·공고 정보 관리 화면

## 4. 확정된 구현 정책

- 추천 제공자는 `RecommendationProvider` 뒤에 두고 `app.recommendation.provider=mock` 설정으로 현재 어댑터를 선택합니다. 교체 제공자는 같은 Mock 공고 카탈로그 식별자를 반환해야 합니다.
- Mock 카탈로그의 기업 매핑 실패는 fixture 오류로 보고 추천 실행 또는 프로젝트 생성을 실패시킵니다.
- 추천 응답은 카드 렌더링에 필요한 기업명·직무·업종·지역·경력·고용형태·마감일·키워드·원문 URL과 점수·순위·근거를 모두 포함합니다.
- 초안 생성은 `202 Accepted` 후 Polling합니다. 접수 후 오류는 `COVER_LETTER_DRAFT.FAILED`에 저장합니다.
- 같은 문항은 활성 생성 한 건만 허용하고, 서로 다른 문항은 최대 4개 작업 스레드에서 동시에 처리할 수 있습니다.
- 서버 시작 시 남은 `PENDING/GENERATING` 초안은 `FAILED(DRAFT_INTERRUPTED)`로 복구해 무한 Polling을 막습니다.
- 새 초안은 기존 초안과 수정본을 덮어쓰지 않습니다. 선택 초안이 없을 때만 첫 성공 초안을 자동 선택합니다.
- 현재 Mock 추천 결과와 생성 스냅샷은 모두 보관합니다. 삭제·만료 배치는 두지 않습니다.
- 입력 제한은 다음과 같습니다.

```text
사용자 이름 100자
자유서술 경험 5,000자
경험 제목 200자, STAR 각 항목 2,000자
경험 키워드 1~20개, 키워드당 100자
직접 입력 문항 1~10개, 문항당 1,000자, 글자 수 조건 1~5,000
additionalInstruction 500자
수정 본문 10,000자
```

## 5. 확정한 LLM 연동 정책

### 우선순위 높음

| 항목 | 선택지 | 권장 시작안 | 영향 |
|---|---|---|---|
| 초안 생성에 사용할 경험 선택 | 현재 전체 후보 전달 후 같은 호출에서 1~2개 선택 / 향후 사전 선별 | MVP는 전체 후보와 본문 생성을 한 번에 처리 | 경험 증가 시 입력 크기 |
| LLM 연결 방식 | Spring 직접 호출 / 별도 AI 서버 | Spring AI로 OpenAI를 직접 호출 | 배포 단위 |
| LLM 제공자·모델 | OpenAI 모델 | 기본 `gpt-4o`, 환경변수로 모델명 교체 | 응답 품질과 비용 |

### 정책 합의

| 항목 | 선택지 | 권장 시작안 | 영향 |
|---|---|---|---|
| 실패 추천 실행 노출 | 기록만 / 사용자 이력에도 표시 | 기록하되 최신 추천에는 `COMPLETED`만 노출 | UI와 장애 분석 |
| 프롬프트·모델 정보 저장 | 호출 메타데이터 저장 | 버전·요청/실제 모델·토큰·지연 시간 저장, 전문 미저장 | 재현성, 개인정보와 저장량 |
| LLM 재시도 | 없음 / 형식 오류·일시 장애만 제한 재시도 | 최초 호출을 포함해 최대 2회 | 응답 시간과 비용 |

## 6. 구현 진행 순서

```text
1. 데모 사용자와 JPA 스키마
2. 경험 저장·조회 및 구조화 인터페이스
3. Mock 추천 응답 보강
4. RecommendationProvider 분리와 추천 실행·결과 저장 API
5. 지원 프로젝트·문항 API
6. CoverLetterGenerator 구현과 문항별 Polling
7. 수정본·초안 선택·검토 상태
8. OpenAI GPT-4o Structured Outputs와 경험 선택 정책 적용
9. 통합·장애·권한 테스트
```

실행에는 `OPENAI_API_KEY`가 필요합니다. 데모 입력 시드는 경험·공고·문항만 준비하므로 초안 생성 버튼을 눌렀을 때 실제 OpenAI 호출이 발생합니다.
